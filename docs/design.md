# 設計書:容量整理のための転送機能

> 状態:草案。「要確認」の項目が決まるまで、実装方式は確定しない。

## 転送対象の選び方

### 目的

使用率が高くなったときに、どのファイルを転送すれば容量が空くかを利用者がすぐ判断し、選べるようにする。

### 画面構成

- **絞り込み**
  - 種類:動画 / 写真(両方選択可)
  - サイズ:下限を指定(例:100MB以上)
  - 期間:撮影日または作成日の範囲
- **一覧**
  - 絞り込んだ結果をサイズの大きい順に表示する
  - 各行にチェックボックス、サムネイル、ファイル名、サイズ、日付を表示する
- **常時表示する情報**(画面上部に固定)
  - 選択中の件数と合計サイズ
  - 転送後の使用率の見込み(例:`85% → 62%`)
  - 見込みは「(現在の使用量 − 選択中の合計サイズ)÷ 総容量」で計算する
- **自動選択ボタン**
  - 「80%未満になるまで大きい順に自動で選ぶ」
  - 絞り込み後の一覧を大きい順にたどり、見込みが80%未満になった時点で止める
  - 一覧の全件を選んでも80%未満にならない場合は、全件を選んだうえでその旨を表示する
  - 自動選択の後も、利用者が手動で外したり追加したりできる

### 権限とスコープ

転送元はDrive上の既存ファイルとする(決定済み)。

- **一覧の作成**:利用者のDrive全体をサイズ順に並べるには、`drive.metadata.readonly` などの権限が必要になる。これは制限付きスコープに当たる。`drive.file` だけでは、アプリが作ったファイルと利用者が選んだファイルしか見えないため、一覧を作れない
- **転送可能フォルダへの移動**:既存ファイルの移動には、そのファイルを書き換える権限が必要になる
  - 制限付きスコープ(`drive` など)を使えば、アプリが移動できる。ただし審査が必要
  - `drive.file` の場合でも、利用者がGoogle Pickerで選んだファイルにはアクセスできるため、アプリが移動できる見込み
- つまり、「移動」より「一覧」のほうが審査の壁になる
- 使用率の「総容量」と「現在の使用量」は、Driveの容量(`about.get` の `storageQuota`)から取る

#### 採用方式:制限付きスコープを取る(決定済み)

検討した方式は次のとおり。この節の画面構成をそのまま実現できるのは方式1だけなので、方式1を採る。

| 方式 | 一覧 | 移動 | 審査 |
|------|------|------|------|
| **1. 制限付きスコープを取る(採用)** | アプリで大きい順に表示 | アプリが移動 | 必要 |
| 2. `drive.file` + Google Picker | Pickerの表示に頼る(サイズ順・使用率の見込みは出せない) | Pickerで選んだファイルをアプリが移動 | 不要 |
| 3. 案内のみ | 出せない | 利用者がDrive上で移動 | 不要 |

#### 使うスコープ

- `https://www.googleapis.com/auth/drive`(制限付き)
  - 一覧を作るだけなら `drive.metadata.readonly`(これも制限付き)で足りるが、既存ファイルの移動もアプリで行うため、書き込みのできる `drive` が必要になる
  - どちらを選んでも制限付きスコープなので、審査の負担は変わらない

#### 審査で求められること(2026-10 時点の公式ドキュメントによる)

- 制限付きスコープの審査(restricted scope verification)を受ける
- ファイルのデータをサーバーに保存または送信する場合は、セキュリティ評価(CASA)も受ける。評価は定期的に受け直す必要がある
- Driveの制限付きスコープを使えるアプリの種類は限られている。対象は、ローカル同期・バックアップのアプリ、生産性・教育のアプリ、レポート・セキュリティのアプリ

### 要確認

1. このアプリ(容量整理のための転送)が、制限付きスコープを使えるアプリの種類に当たるか。当たらないと判断されると審査に通らないため、審査の申請前に確認する
2. ファイルのデータをサーバーに保存・送信するか。しない構成(端末内で完結)にできれば、セキュリティ評価を省ける可能性がある
3. `about.get` の `storageQuota` を `drive` スコープで取得できるか(取得できる見込み)
4. 転送可能フォルダの場所と、そこへ移した後の扱い
